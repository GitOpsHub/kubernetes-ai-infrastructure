Chapter 05 · Model Storage and Data

EBS, EFS and S3 mounts on EKS — how each one actually works

Three animated walkthroughs of the storage patterns in 05-model-storage-and-data: a zonal block volume that a spot reclaim can strand, a regional NFS filesystem every AZ can share, and an object bucket mounted keylessly through EKS Pod Identity. Watch the moving dots — they trace the same request path the chapter README walks through in prose.

Pattern (b)

Amazon EBS — a zonal disk, one attachment at a time

A PVC on the default StorageClass provisions a real EBS gp3 volume. It lives in exactly one Availability Zone and can be attached (ReadWriteOnce) to exactly one node's kernel at a time — great for a single steady replica, a trap the moment spot reclaims the node it's plugged into.

  1. 1 A PVC on the default StorageClass gets a real, single-zone EBS gp3 volume — provisioned once, in the same zone as whichever node first claims it.
  2. 2 The volume attaches ReadWriteOnce: exactly one node's kernel can hold the attachment at any moment, which is fine for one steady replica.
  3. 3 Spot reclaims the node. The Deployment reschedules the Pod — often onto a node in a different AZ, because the scheduler has no reason to prefer the old one.
  4. 4 The new node tries to attach the same volume and fails outright (Multi-Attach error) — an EBS volume simply cannot cross Availability Zones.
Pattern (d)

Amazon EFS — one regional filesystem, mounted from every AZ at once

EFS is managed NFS: a mount target in every AZ your nodes might land in, all pointing at the same file system. Any number of pods, in any zone, mount it ReadWriteMany with normal POSIX semantics — in-place edits, renames, concurrent writers — the exact thing an EBS volume can't do.

  1. 1 The efs-models StorageClass makes the PVC dynamically provisioned: the EFS CSI driver's controller creates an access point per PVC automatically.
  2. 2 A mount target (an ENI on port 2049) sits in every AZ your subnets cover — that's what makes the file system reachable from wherever a node lands.
  3. 3 A populate Job writes once; two or more serving replicas mount the same PVC ReadWriteMany, concurrently, even across different nodes and zones.
  4. 4 A spot reclaim just moves a Pod to a new node in a new AZ — the mount target there already exists, so nothing breaks the way it did for EBS.
Pattern (c) · default

S3 via Mountpoint — a bucket, a FUSE process, and a credential nobody wrote down

Mountpoint for S3 is a CSI driver plus a FUSE program that makes a bucket look like a read-only directory. There's no static access key anywhere: EKS Pod Identity exchanges the Pod's own short-lived Kubernetes token for a short-lived AWS credential, on every mount.

  1. 1 Kubernetes mints a fresh, short-lived JWT for the Pod's ServiceAccount (model-reader), scoped to audience eks.amazonaws.com — it's never written to a Secret.
  2. 2 The on-node Pod Identity agent hands that JWT to AWS STS's AssumeRole, which checks it against the Pod Identity association you created for this namespace + ServiceAccount.
  3. 3 STS returns a temporary AWS credential, valid for a limited window and refreshed automatically — the same kind of key a human's static key would be, minus the "valid forever" part.
  4. 4 Mountpoint uses that credential to open parallel range reads against the bucket — no in-place edits, no rename, no overwrite by default, which is exactly right for immutable model weights.

Cheat sheet

EBS (RWO PVC)
Zonal · one node at a time
Fast, cheap
Breaks on cross-AZ spot moves
Fits: single replica, single zone
EFS (RWX)
Regional · every AZ
Real POSIX semantics, concurrent writers
Higher cost, mount-target setup
Fits: shared datasets, checkpoints
S3 + Mountpoint
Regional · any node, any zone
Read-mostly, parallel, keyless auth
No rename/overwrite by default
Fits: production model serving (default)
